## Problem Statement
새 기능이나 사이트를 쓰려면(개발자·비개발자 공통) 매뉴얼, 검색, 유튜브를 뒤져야 하는데 원하는 목표를 끝까지 이루는 것이 생각보다 어렵다. 에이전트에게 맡기자니 무엇을 하는지 모르는 상태가 미심쩍다. 해결안은 gahelper(크롬 확장 "Setup Copilot": 사용자가 직접 조작하고 확장은 화면을 읽어 한 단계씩 안내·검증)가 gadgetarms.com에 등록된 레시피(의도만 적은 goal 목록)를 실행하게 하는 것이다. 이 문서의 결정 범위는 **첫 단계(A): 사이트 없이 러너를 검증하고 사람을 관찰하는 것**이다.

## Demand Evidence
없음(Q1: "아직 증거 없음"). 저장소에 사용자·결제·재사용 흔적이 없다. 러너 검증 결과도 없다.

## Status Quo
검색, 유튜브, 블로그를 보고 따라하기(Q2). 무료이고 익숙하다. UI가 바뀌면 낡는다는 것은 **가설이며 관찰된 사례가 없다**(H2). 에이전트형 대안은 별도 존재한다(출처: [Kilo](https://kilo.ai/articles/best-ai-browser-extensions)).

## Target User & Narrowest Wedge
- 타깃: "본인 또는 가까운 사람"(Q3). 실명, 직함, 곤란한 상황은 아직 없다. 개발자·비개발자를 모두 포함한다고 했으나 첫 관찰 대상은 해당 서비스를 설정해 본 적 없는 사람이다.
- 쐐기: 사이트 없이 **이미 있는 러너**로 레시피 R01~R10이 실제 화면에서 끝까지 가는지 측정하고, 비개발자 5명을 관찰한다.

## Hypotheses (사실이 아니라 검증 대상)
- H1: 사람들은 목표 달성과 함께 "무엇을 하는지 이해·통제"하기를 원하며, 에이전트 일임에는 미심쩍음이 남는다.
- H2: 의도만 적은 레시피는 UI 변경에도 낡지 않는다. 반증 시험: UI가 두 번 바뀐 뒤에도 UI 힌트 없이 완주되는가(담당: 개발자 본인, 단계: B 이전 실화면 재시험).
- H3: 레시피 레지스트리는 유통 채널·해자가 될 수 있다. B 이후 검증.
- H4: 에이전트(Claude for Chrome 등) 대안이 있어도 안내형이 선택된다. A의 관찰에서 측정.

## Decision rule (관찰 전에 고정, 사용자가 시작 전에 숫자를 바꿀 수 있음)
행동 입력은 **세션 후 질문 하나**로 고정한다(아래 Understanding/control/trust의 Q2). 세션 전에 묻는 "안내받을래요, 대신 해 줄까요?"는 기준선으로만 기록하고 규칙에는 쓰지 않는다(대신 해 주는 모드를 보여주지 않은 가정 질문이라서).

**이 규칙은 파일럿 휴리스틱이며 통계 검증이 아니다**(eng review run 3, R7). 표본이 작아 신뢰구간이 넓다(정확 이항 95%): 8/16 = 24.7~75.3%, 3/5 = 14.7~94.7%, 4/5 = 28.4~99.5%. 또 완주율 조건은 dev 6회와 nondev 10회를 합친 값이라 dev가 6회 모두 성공하면 nondev 진짜 완주율이 20%여도 약 62% 확률로 통과한다. `scripts/eval-report.js`가 각 비율의 95% 구간과 nondev 하위 합계를 결과표에 **보고만** 하며 게이트로 쓰지 않는다.
- **참가자 단위(R9)**: 판정 단위는 참가자 5명이고, 한 참가자가 아래 조건(B 조건 5의 항목, 피벗형)으로 세어지려면 그 참가자의 **두 회차 코드가 모두** 조건을 만족해야 한다. 코드가 하나라도 없으면 미충족으로 세고 보고에 "코딩된 회차 n/2"를 표시한다.
- **판정 순서(R8)**: 피벗 조건이 성립하면 B 조건 충족 여부와 무관하게 판정은 피벗이다. 결과표는 항상 하나의 판정만 낸다.
- **데이터 완전성(R13)**: 아래 "계획 run 명단"(20회)의 모든 run이 종결 상태(`completed`/`abandoned`/`rejected`/`crashOrHang`)이고 기록이 있어야 판정한다. 기록이 없는 계획 run, 명단에 없는 기록, `in_progress`가 하나라도 있으면 판정은 "불완전(INCOMPLETE)"이며 B 진행도 피벗도 내지 않는다. 관찰자가 체크시트에서 막힌 run을 `abandoned` 또는 `crashOrHang`으로 종결한다. 종결은 체크시트(관찰자 기록)에만 쓰이므로 `eval-report`는 **효과 상태 = 관찰자 종결 ?? run 기록 상태**로 읽는다. 종결은 `in_progress` run에만 가능하고 되돌릴 수 없으며, 종결 뒤 러너 쪽 이벤트는 상태를 바꾸지 못하고 보고서에 개수로만 표시된다. 내보내기의 기록 건강 상태에 쓰기 실패나 부착하지 못한 이벤트(`failed`, `unmatched`)가 있으면 같은 이유로 판정은 `INCOMPLETE`다(`late`·`dup`은 손실이 아니다). 패널을 다시 열 때 시스템이 `reconcile`로 닫은 `abandoned` run은 관찰자가 한 번 `crashOrHang`으로 덮을 수 있다.

- **B로 진행** (모두 충족):
  1. 레시피 완주율 50% 이상(R01~R06 16회 중 8회 이상).
  2. 허위 완주 1건 이하(관찰자 확인 기준, 아래 정의).
  3. 비밀값 LLM 전송 0, OAuth 팝업 후 재개 성공(R07, R09 dev), payload LLM 미포함(R10 dev).
  4. **게이트 v2 기준**: 관측되지 않은 라벨의 사용자 노출 0, 크래시·무한 대기 0(`blocked`뿐 아니라 첫 resolver 요청이 돌아오지 않는 경우를 포함하며 러너 상태와 무관, 관찰 메모와 evallog의 `crashOrHang`로 확인; eng review run 3 재검토).
  5. nondev 5명 중 3명 이상이 (Q2 "안 맡김") 또는 (Q3 "혼자 할 수 있음" = 예 그리고 Q1 1 이상). 참가자 단위 집계는 위 R9 규칙을 따른다.
- **중단 또는 피벗**: R01~R06의 goal 단위 완주율 30% 미만(부록 R7: v2 가정 재검토), 또는 nondev 5명 중 4명 이상이 Q2 "맡김"이고 이유 코드가 "귀찮음/보기 싫음"인 경우(피벗안: 대신 해 주되 무엇을 하는지 설명하는 모드).
- **그 외**: 부분 통과이므로 같은 구성으로 한 번 더 관찰한 뒤 다시 판단한다. 2차 관찰은 모든 run 기록의 `evalRound`를 2로 두고, 계획 run 명단 대조와 판정은 라운드마다 따로 하며 라운드를 풀링하지 않는다(2차 라운드 판정이 최종이다, eng review run 3).
- **정보용(게이트 아님)**: 부록 R6의 v2 기준 중 goal 완주율 60% 이상과 resolver 응답 p50 6초 이하는 `resolverMs`와 함께 보고만 한다(60% 미만이어도 30% 이상이면 중단하지 않음).
- **허위 완주** = `done`이면서 **관찰자가 `manualCheck`를 직접 확인했을 때 실패**인 회차. 참가자의 "실제로 됐나요?" 답과 관찰자 판정이 다르면 불일치로 따로 센다. 판정은 evallog의 `observerVerified` 필드에 기록한다(부록 R4.7의 `userConfirmedReal`에 더해 추가하는 필드).
- **H4(에이전트 대안과 비교)**: 이번 단계에서는 **측정하지 않는다.** 에이전트 대안을 보여주지 않으므로 Q2의 가정 질문으로만 근사한다.

## Understanding / control / trust 측정 (H1)
각 nondev 회차 직후 관찰자가 3가지를 묻고 코딩한다.
1. "방금 무슨 일이 일어났는지 설명해 보세요." 0 = 설명 못함, 1 = 부분적, 2 = 정확.
2. "이 일을 대신 해 주는 도구였다면 맡겼을까요? 왜요?" 맡김/안 맡김 + 이유 원문 기록. 이유 코드: 불신·불안, 귀찮음·보기 싫음, 배우고 싶음, 기타(원문 병기). 여러 이유면 첫 번째 이유를 코드로 쓴다. **이 질문이 Decision rule에 들어가는 유일한 행동 입력이다.**
3. "다음에 비슷한 설정을 혼자 할 수 있을 것 같나요?" 예/아니오.
결정 규칙의 3번은 **"혼자 할 수 있음(자립 가능, 이해·통제 성과)"**이다: 3번이 '예'이고 1번이 1 이상인 경우(eng review run 3, R10). 이 질문은 이 도구를 **다시 쓰겠다**는 의향을 재지 않는다("혼자 할 수 있다"는 오히려 도구가 필요 없다는 신호일 수 있다). 재사용 의향과 수요 증거는 이번 단계에서 측정하지 않으며 계속 없다.

## Participants, safety, and privacy
- **선정 기준**: 해당 서비스(API 키, 맞춤 지침, 지메일 필터 등)를 설정해 본 적 없고, 이 도구를 본 적 없는 사람. 관찰자와의 관계(가족/친구/동료)를 기록하고, 결과를 읽을 때 호의 편향을 감안한다.
- **계정(부록 R5·R8 준수)**: 관찰한 **모든** 회차는 테스트 전용 또는 일회용 계정과 **전용 브라우저 프로필**에서 한다. 개인·회사 계정은 쓰지 않는다. 개발자가 계정을 미리 만든다(R05에 필요한 두 번째 공유 대상 계정 포함).
- **동의 안내(시작 전 구두)**: (1) 세션을 관찰하고 메모한다. (2) 화면에 보이는 내용이 LLM 제공자에게 전송된다. (3) 로그는 이 기기에만 저장되고 결정 후 삭제한다.
- **세션 후 정리**(순서 중요, eng review run 3, F9): (1) `eval-report`용 JSON을 내보내고 파일 저장과 기록 수(20회 명단 대비)를 확인한 **뒤에만** (2) 만든 키·필터·공유 삭제 또는 해제(레시피의 `manualCheck`에 "테스트 후 키 삭제" 등 이미 명시), (3) 옵션 페이지의 테스트용 LLM 키 제거와 필요하면 폐기·교체, (4) 진행 중인 레시피 세션만 정리하고 **`sc.evallog.*` 기록은 지우지 않는다**(20회를 한 전용 프로필에 누적하고 `sc.evallog.*`는 최종 보고서 확인 후 한 번 삭제, eng review run 3 R18). 세션마다의 내보내기 파일은 프로필 손상에 대비한 백업이고 `eval-report`는 마지막 내보내기 하나를 입력으로 쓴다. 기록 삭제는 내보내기 확인 전에 하지 않는다(기록이 보고 전에 사라진다).
- **evallog 기록 내용(부록 R4.7과 동일)**: 기록하는 것은 goal별 결과, 화면 수, `resolverMs`, `guardRejects` 이유, `blockedCause`, `popupPauses`, `userConfirmedReal`, 추가 필드 `observerVerified`·`crashOrHang`, 소요 시간. **기록하지 않는 것은 화면 텍스트, signature, goalText 외의 사용자 입력, 비밀값**이다. `lib/evallog.js` 테스트는 이 제외 규칙(특히 R06·R08에서 화면에 뜨는 키)을 검증해야 한다.
- 관찰 메모에는 이름 대신 P1~P5를 쓴다.
- **"수동으로 진행"(skipped)**: 부록 R4.2에 따라 완주가 아니다. 막히면 누르게 하는 것은 의도된 규칙이며 레시피 완주율에서 미완주로 집계한다.
