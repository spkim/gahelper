# lesson 레시피 설계 (한 장)

> **상태: 관찰 후 갱신.** Stage A 관찰 전에 쓴 초안이라 근거가 없다. 아래 내용은 가설과 열린 질문이며, 구현하지 않는다(코드 없음). 관찰 결과가 나오면 맨 아래 "갱신 트리거"에 따라 고치거나 버린다.

## 1. 무엇인가
`lesson`은 **AI 사용법을 배우는 안내**다("프롬프트에 역할을 주면 답이 어떻게 달라지는지 해 보기" 같은 것). `setup`이 "이 화면에서 이 설정을 끝낸다"라면, `lesson`은 "사용자가 무언가를 이해한다"가 목표다. 입력 설계(`recipe-registry-runner-first.md`)는 이것을 B/C 단계로 미뤘고, 이 문서는 그때 다시 시작할 수 있도록 차이만 적어 둔다.

## 2. `setup`과 다른 점
| | `setup` (지금 있음) | `lesson` (가설) |
|---|---|---|
| 성공의 뜻 | 화면 상태가 바뀜(키가 생김, 필터가 생김) | 사용자가 이해하거나 할 수 있게 됨 |
| 검증 | 단계마다 `verify`(화면에서 관측 가능한 조건)와 `guard`. 최종 확인은 레시피의 `manualCheck`를 관찰자가 직접 본다 | 화면 상태로는 판정하기 어렵다. 같은 화면이 나와도 이해했는지는 모른다 |
| 완주의 증거 | 모든 goal `done`, 수동 진행 없음, 관찰자 확인(`observerVerified`) | 후보: 사용자가 자기 말로 설명(자기 보고), 짧은 퀴즈, 결과물 비교. 모두 사용자 입력이 필요하다 |
| 개인정보 | 화면 구조만 LLM으로 가고, 스크럽은 content script 안에서 한다(`spec-v2.md` 원칙 6). 사용자 입력은 `goalText`뿐이고 evallog는 비밀값·화면 텍스트·`goalText` 밖의 사용자 입력을 기록하지 않는다 | 학습 내용 자체가 사용자의 글이다(연습 문장, 퀴즈 답, 설명). 기록하면 위 제외 규칙과 정면으로 충돌한다 |
| 실패의 비용 | 엉뚱한 버튼을 짚음. 사용자가 실행 주체라 되돌릴 수 있다 | 잘못 가르침. 되돌리기 어렵고 사용자가 알아채지 못할 수 있다 |

핵심 차이는 둘이다. **(1) 검증:** `setup`의 안전망은 "화면에서 관측된 것만 말한다 + verify가 통과해야 진행"인데, `lesson`에는 관측 가능한 성공 조건이 없다. **(2) 개인정보:** 이해를 확인하려면 사용자가 쓴 것을 봐야 하고, 그것을 남기는 순간 현재 원칙과 부딪힌다.

## 3. `type` 필드 활용
`lib/recipe-store.js`의 레시피에는 이미 `type: "setup"`이 있다. 다만 현재 `validateRecipe`가 `setup` 외의 값을 **예외로 거부**하고, 러너·패널은 `type`을 분기에 쓰지 않는다. 그래서 `lesson`을 넣으려면 최소한 다음이 필요하다(전부 미구현, 결정도 아님).
- 스키마: `type: "lesson"`을 허용하되 `goals[].label`(무엇을 이루나)이 아니라 학습 목표와 확인 방식을 담는 필드가 따로 필요하다. `setup`의 `manualCheck`와 `site`는 의미가 맞지 않는다.
- 러너 분기: `verify` 없이 진행하는 경로를 만들면 "verify는 생략하지 않는다"는 원칙을 `lesson`에서만 예외로 두는 셈이다. 예외를 두지 않으려면 `lesson`은 다른 러너여야 한다.
- 린트: `test/helpers/recipe-lint.js`는 `goals`가 비면 위반이다(`generic-setup` 예외). `lesson`이 들어오면 규칙을 `type`별로 나눠야 한다.

## 4. 열린 질문 (관찰하지 않았으므로 답이 없다)
1. 화면 상태가 아닌 무엇을 성공으로 볼 것인가? 자기 보고는 호의 편향에 약하다(Stage A에서도 같은 약점을 인정했다).
2. 학습 기록을 어디까지 남길 것인가? 안 남기면 효과를 못 재고, 남기면 원칙이 바뀐다. "기기 밖으로 나가지 않는다"만으로 충분한지도 모른다.
3. 레시피를 누가 쓰는가? `setup`은 개발자가 손으로 쓴 번들만 실행한다. `lesson`은 내용의 정확성이 안전과 직결되어 서명·검토 부담이 더 크다.
4. 사용자가 `setup`보다 `lesson`을 원하는가? 이번 단계는 재사용 의향과 수요를 재지 않는다(Q3 "혼자 할 수 있음"은 도구를 다시 쓰겠다는 뜻이 아니다).

## 5. 이 문서가 하지 않는 것
- 구현, 스키마 확정, 러너 변경.
- 수요 주장. 위 표의 "후보"와 "가설"은 근거가 아니라 출발점이다.
- gadgetarms 레지스트리나 서명 설계(B 단계 문서의 몫).

## 6. 갱신 트리거 (Stage A 관찰 뒤)
- **Q3 "혼자 할 수 있음"이 예이고 Q1이 1 이상인 nondev 참가자가 많다:** 도구보다 이해가 문제였을 수 있다. 질문 1·4를 먼저 본다.
- **Q2 "맡김 + 귀찮음"이 몰린다(피벗안):** `lesson`보다 "대신 해 주되 설명하는 모드"가 우선이다. 이 문서는 보류한다.
- **"배우고 싶음" 이유 코드가 눈에 띄게 나온다:** 질문 4의 약한 신호. 이때만 이 문서를 `lesson` 설계의 입력으로 다시 연다.
- 어느 쪽도 아니면 이 문서는 그대로 두고, 근거가 생길 때까지 구현 후보에 올리지 않는다.
